## Where the button art lives
Every prompt is a tiny loose texture: `Content/Tooltip/*.xnb` (in-game tooltips, 28x23, 2661 bytes; HOLD is 26x11) and
`Content/Menu/xbox/*.xnb` (menus: 13x13 face buttons, 17x15 pills). All of them are XNB v5, platform `w`, not compressed,
one `Texture2DReader`, surface format 0 (Color): an **85-byte header followed by raw RGBA** (straight alpha, rows top-down,
a fully transparent pixel is (0,0,0,0)); the file ends at the last pixel, so `size == 85 + width*height*4` and **there is no
spare byte** (no marker is possible). `py_modules/button_glyphs/xnb.py` reads and rewrites them (`parse`, `pixels`,
`with_pixels`; 413 Texture2D files of the real build round-tripped byte-identical).

There is no PlayStation art and no code switch (the game has one prompt path, `Menu/xbox/`; the Switch sets
`Tooltip/Switch/` and `Menu/switch/` belong to a port that is dead on PC). Recon found no community mod. So the art has to be
replaced.

36 textures carry prompts (`profiles/songs_for_a_hero_cells.py`, generated by `tools/sfh_build.py`, with the measured cells
as the spec) plus one unreferenced duplicate with a typo in its name (`Menu/xbox/rstrick`, out of scope).

## What the profile changes (and what it leaves alone)
**Changed, 24 files (46,928 bytes in all):** each is replaced whole by the user's PlayStation pixel-art picture of exactly
the same size (`masks/sfh/<Folder>_<name>.png`, listed in the generated `songs_for_a_hero_art.py`).

| Group | Files | Becomes |
|-------|-------|---------|
| Tooltip faces | `Tooltip/A B X Y` | ✕ ○ □ △ |
| Tooltip D-pad | `Tooltip/Dpad`, `DpadUp/Down/Left/Right` | PlayStation D-pad (small arrow marks) |
| Tooltip shoulders and triggers | `SHOULDER_LEFT/RIGHT`, `TRIGGER_LEFT/RIGHT` | L1 R1 L2 R2 (a 3x5-pixel font) |
| Tooltip START | `Tooltip/START` | the OPTIONS icon (icon only, no word) |
| Menu faces | `Menu/xbox/a b x y` | ✕ ○ □ △ (dark discs) |
| Menu pills | `Menu/xbox/lbumper rbumper ltrigger rtrigger` | L1 R1 L2 R2 |
| Menu START/BACK | `Menu/xbox/start`, `select` | OPTIONS and SHARE icons |

Rendering is: the original file with its pixel block replaced wholesale by the picture's pixels (the header is untouched,
the length is the same). Transparent pixels stay (0,0,0,0).

**Left alone, 12 files** (they look the same on a PlayStation pad, or the user's sheet had nothing better): `Tooltip/Hold`,
`Tooltip/LEFT_STICK_*` (5), `Menu/xbox/dup ddown dleft dright` (arrows), `Menu/xbox/lstick rstick` (stick caps). Everything
else in `Content/` (8,500+ files) is never opened.

### Provenance of the art
The pictures are the user's own redrawn PlayStation art (a sheet of 39 icons). The origin of the pixels is **not stated**.
`tools/art_overlap.py` found 0 pixels identical to the game's own textures (reported by the orchestrator; not re-run for
this page). The source sheet is not in the repo (`tools/sfh_art.py` slices it into the 24 native-size PNGs). The PNGs are the
only art the repo carries for this game; no game art is copied (tools emit hashes and sizes, never pixels).

## How state is detected without a marker
State is read per file from SHA-256 (`files_patch.classify`), so it survives a lost `config.json` and Steam restores. Because
an XNB has no spare byte, "who wrote these bytes" is answered by a small **ownership ledger**, not by the file:
`backups/389170/files/renders.log`, one line `<sha256> <profile revision>` per render, written (atomic rewrite, fsynced,
de-duplicated, capped at 4096 lines, a torn or damaged line ignored) **before the first game file of an apply is written**.

| State | The file is | What happens |
|-------|-------------|--------------|
| original | byte-equal to the pinned original | PlayStation: backed up, then drawn. Original: nothing to do |
| patched | byte-equal to the render of its backed-up original with today's art | PlayStation: nothing to do. Original: restored |
| stale | not original and not today's render, but its SHA-256 is **in the ledger** (we wrote it once), it keeps the original's size and header, and a verified backup exists: an older drawing of ours (art or profile changed after the install) | PlayStation: **rebuilt from the backup**, never from the stale file (styles cannot stack). Original: restored |
| orphan | ours (equal to today's render, or in the ledger) but no verified backup exists (plugin data lost) | error, nothing touched; Steam > Verify files turns it into an original and the plugin recovers |
| unknown | anything else: another build, **a game update that changed only the pixels**, an edited, truncated or non-regular file, an old drawing whose ledger was lost | PlayStation: refused, **nothing at all is written**, the error is shown. Original: left alone (not ours), but the status says so (below) |
| missing | not there | PlayStation: refused. Original: left alone, and counted in the same status message |

"Unknown" is not a dead end: Steam "verify files" and updates restore a file to the pinned original, which the watcher draws
again within a minute. The profile `revision` is informational for this strategy: a changed picture or render is found by
content (stale), so a forgotten bump cannot leave old art in place (bump it anyway).

**Under Original, a file that is not ours must not read as "ok".** When the plugin has handled the game before (a backup
folder exists, or the config records an apply), the status becomes an error such as "2 of 24 files are not the supported build
(a game update, or art left by a lost plugin install); Steam > Verify files helps only in the second case" (after a real game
update Verify brings back the NEW build, not the pinned one), while the files that ARE ours are still restored. It outranks
"pending" (and yields to running / updating). For a game the plugin never handled it is only a notice (state `ok` with the
message "N of 24 files are not the supported build (the game was probably updated); PlayStation cannot be applied"; the status
model has no separate notice level). It is computed from the files each time, so nothing is rewritten and the watcher stays idle
because of it (`sync_all` only syncs a game with a style chosen or with restorable files). If both the config and the plugin's
data are lost, nothing says the plugin was there, so only the notice can be given.

**How the stale limit changed.** The first version called "same size, same header, valid backup, other pixels" a stale
drawing of ours. A game update that changes only the pixels of one texture looks exactly like that, and Original (and the watcher)
would have put the OLD original back over a file we did not write. Now only a hash in the ledger can be stale; such a file is
unknown, left alone, and PlayStation is refused until Steam > Verify files. The price: **if the ledger is lost** (the plugin's
data folder is wiped) while backups survive, files drawn with an older picture become unknown (PlayStation refused with the
"Verify files" hint; Original leaves them and says so). That is the safe side. Files that equal today's render stay "patched"
without any ledger. (Tests: `LedgerTest`, `OriginalWarningTest`.)

### Write order and undo
1. every one of the 24 files is read and classified; a missing or unknown file stops the run before any write;
2. the art preflight loads all 24 PNGs and checks that each has exactly its texture's size (a missing or damaged picture stops
   here, with no backup and no write; Original still works with the art gone);
3. the **whole original file** of every pristine file is saved to `backups/389170/files/<Folder>_<name>.orig` (temp file,
   fsync, rename, fsync of the folder), read back and compared with the pinned SHA-256; free space is checked;
4. every new file is rendered from a verified backup (a bad render writes nothing); the SHA-256 of every render is recorded in
   the ledger; then each file is replaced atomically (temp file in the same folder, fsync, `os.replace`, fsync of the folder)
   and read back; stale `*.button-glyphs.tmp` files of a crashed run are removed first; a crash between the ledger and the
   first file only leaves hashes of files never written (harmless);
5. undo writes the verified backups back the same way, **in reverse order**, and checks every restored file against the pinned
   SHA-256. Backups are never deleted, so a second Original is a no-op.
Whatever the moment of a power cut, each file is either original or fully drawn; the next sync completes the job, or Original
restores it.

All reads are bounded to the pinned size plus one byte. The engine does nothing while the game runs or while Steam updates it;
the watcher retries every minute. An Original chosen while the game was running is finished by the watcher too
(`Engine._files_restore_pending`).

### The running-game guard (shared core)
`steam.is_running` is used by every strategy. It used to look for the install path as a plain substring of a process command
line, which missed a game started through another name of the same SD card. It now also looks for (it can only see more, never
less): the path's realpath; the mount aliases `/run/media/<user>/<label>` and `/run/media/<label>` (derived only for a path under
`steam.MEDIA_ROOT` that has a `steamapps` folder, and only when the alias exists and is the very same folder); each of those in
the `Z:\...` form Proton uses; and the launcher's `AppId=<appid>` token as a whole token (`AppId=3891700` is not 389170). Folder
names are compared as they are, with no Unicode normalisation. (Tests: `tests/test_running_guard.py`.) On the Deck the exact
form the game's process uses is still to be read (see caveats).

## How it is verified
`tests/test_files_patch.py` (synthetic fixtures: fake XNB files built with the `tests/test_xnb.py` builder, tiny fake pictures,
a fake Steam library with an accented install folder) and `tests/test_songs_for_a_hero.py` (the real table and the real bundled
pictures); `tests/test_running_guard.py` covers the guard. Highlights: whole-tree SHA-256 equal after ps -> original -> ps ->
original; crash injection after k files while applying, restoring and backing up (every k), between the ledger and the first
file, and while writing the ledger; states original / patched / stale / orphan / unknown / missing; Steam verify and partial
restores; art changed after an install (rebuilt from the backup, blend-style render fed the pristine original); a game update
that changes only pixels (not overwritten, error shown, nothing written); the plugin data lost and a later art revision; a torn
or oversized ledger; refusal with every file untouched; preflight failures write nothing; status order running > updating > error
> pending > ok; write, restore and backup read-back errors; free space; a second apply writes nothing; bounded reads. The 24 real
PNGs are checked against the table (exact size, alpha only 0/255, transparent pixels (0,0,0,0)).

## Open questions and caveats
- Where the game runs from: the library path Steam reports and the path in the game's process may be two mount names of the
  same SD card (the recon notes name both `/run/media/LX512` and `/run/media/deck/LX512`). The guard now derives the other
  mount name and the realpath (see "The running-game guard"), and also recognises Steam's `AppId=389170` launcher. Still read on
  the Deck, before the first real apply: the game's `/proc/<pid>/cmdline`, the card's filesystem (an exFAT card has no crash
  safety for renames) and the owner of the files (new files keep the mode of the old, not the owner). Replacing a file by
  rename is safe even if the game had it open.
- The profile never opens the Switch sets, the `Hud/ControllToolTip` or `Menu/Controles` pictures, or the options screen
  (key rebinding only): not scanned for pad pictures beyond the recon notes.
- A plugin downgrade to a profile that does not know the strategy would leave the drawn files in place until Original is chosen
  with the new plugin; Steam > Verify files restores all of them.
- Steam updates restore only the files that changed in a build; our drawn files stay drawn.

## How to re-derive the data
`tools/sfh_build.py <Content dir>` (stdlib; run it on a copy of the real `Content/`) regenerates
`profiles/songs_for_a_hero_cells.py`; `tools/sfh_art.py <sheet.png> --content <Content dir>` slices the user's sheet into
`masks/sfh/*.png` and writes `songs_for_a_hero_art.py`; `tools/art_overlap.py <masks/sfh> <Content dir>` measures how many
pixels the pictures share with the game's. The originals are only read.

## Learnings
- Loose tiny files with no spare byte cannot carry a marker: pin the whole-file SHA-256, back up the whole file, and decide
  the state by comparing with the original and with today's render. "Same size and header, other pixels" is NOT proof of
  ours (a game update looks the same): an older drawing is "stale" only if its hash is in an ownership ledger written before
  the files; anything else is "unknown".
- Steam's library path and the game's process path may be two mount names of the same SD card: before the first apply, check that the game's /proc cmdline contains the exact install path steam.is_running compares. _(Songs for a Hero, 2026-11-24)_
