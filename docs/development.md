# Development guide

Everything you need to build, test and run Button Glyphs. For *what* the code does, read [architecture.md](architecture.md);
for adding a game, [adding-a-game.md](adding-a-game.md).

## Setup

You need **Node.js 20+**, **pnpm 9+** and **Python 3.9+**. The backend uses only Python's standard library (the Deck has no pip), so there is nothing to install for it.

```bash
git clone https://github.com/evertonfxavier/button-glyphs.git
cd button-glyphs
pnpm install
```

## Everyday commands

| Command | What it does |
|---------|--------------|
| `python3 -W error::ResourceWarning -m unittest discover -s tests` | All backend tests (about 15 s). They never need game files. `-W error::ResourceWarning` makes unclosed files fail. |
| `pnpm test` | The same, through pnpm |
| `npx tsc --noEmit -p .` | Type-check the UI |
| `pnpm run build` | Build the UI into `dist/` |
| `pnpm run build:zip` | Build `out/button-glyphs-vX.Y.Z.zip` (the file users install) |
| `pnpm run glyphs` | Re-render the icon PNGs and `src/generated/glyphs.ts` from `assets/svg/` |
| `pnpm run brand` | Re-render the logo and the social preview from `assets/logo.svg` |
| `python3 tools/gen_supported_games.py` | Refresh `SUPPORTED_GAMES.md`, the one place that lists the games (tests fail if it is stale) |
| `python3 tools/build_button_catalog.py build` / `find --role a --size 13x13` | Refresh `catalog/catalog.json` + `docs/button-catalog.md` (tests fail if stale) / look up the closest existing button |

## Project map

| Path | What |
|------|------|
| `main.py` | Decky entry point: callables for the UI and a background watcher (every minute) |
| `src/` | The React UI: game select, style select, preview, status |
| `py_modules/button_glyphs/engine.py` | State, status, apply and restore, choosing the strategy per game |
| `py_modules/button_glyphs/entries.py` | Strategy: append a new archive entry and repoint the index |
| `py_modules/button_glyphs/region_patch.py` | Strategy: rewrite fixed byte ranges in place |
| `py_modules/button_glyphs/profiles/` | One module per game, plus the strategy classes |
| `py_modules/button_glyphs/{forge,image,trailer,steam}.py` | Archive format, pixels (DXT/PNG), the file marker, Steam libraries |
| `assets/svg/{ps,xbox}/` | Icon sources, one SVG per button |
| `py_modules/button_glyphs/glyphs/`, `src/generated/` | **Generated** from the SVGs: never edit by hand |
| `tools/` | Developer tools that derive game data from real files, scaffold new games, validate profiles |
| `tests/` | Synthetic-fixture tests |
| `docs/` | These guides, the architecture, and one page per supported game |

Files marked "Generated by … do not edit" are produced by a tool; change the tool or its input, then regenerate.

## Tests: what is covered

- **Strategies** (`test_backend.py`, `test_entries.py`, `test_regions.py`): apply per style, exact undo, refusal of unknown layouts, re-apply after an update, recovery after a crash, never touching a running game.
- **Tools** (`test_scaffold.py`, `test_clone_validate.py`, `test_verify_profile.py`, `test_deck_probe.py`, `test_supported_games.py`): the scaffold makes importable skeletons; clone validation catches a broken undo; the supported-games files are up to date.
- **Repository health** (`test_repo_health.py`): the community files exist, every relative link in the Markdown files works, the changelog mentions the current version.

CI runs all of them on every push and pull request.

## Working with a real Deck

You do not need SSH to test: build the zip (`pnpm run build:zip`), copy it to the Deck, and use **Install Plugin from ZIP** in Decky's Developer settings. With SSH
you can iterate much faster and read logs.

### Turn SSH on (once)
In **Desktop Mode** open Konsole and run:

```bash
passwd                                  # set a password for the user "deck" (needed the first time)
sudo systemctl enable --now sshd        # start the SSH server now and on every boot
ip -4 addr show | grep inet             # find the Deck's address (Wi-Fi is usually wlan0)
```

Then from your computer: `ssh deck@<address>`. If you get *Connection refused*, SSH is off (it is the SteamOS default): repeat the steps above.
A SteamOS update may switch it off again.

### Safe habits
- **Analyse on your computer.** Copy files with `scp deck@<address>:<path> ./work/`; do not edit game folders by hand.
- **Look before you install.** Load your new build from a temporary folder against the real config and print what each game would do (`Engine.list_games()` is read-only) before replacing the plugin.
- **Installing makes the plugin act.** As soon as it loads, the watcher applies the styles you chose to the games in your library. Close games first.
- **Logs:** `~/homebrew/logs/Button Glyphs/` and `journalctl -u plugin_loader`.

## Verifying a profile

Two tools turn the verification that used to be rewritten for every game into commands. Neither needs the Deck to be writable; the second only reads.

```bash
python3 tools/verify_profile.py <appid> <folder with the real copies> [--json report.json] [--only cycle,crash] [--quick] [--keep] [--sheet DIR]
python3 tools/deck_probe.py <appid> [--json out.json]        # the Deck must be awake: .claude/scripts/deck.sh --check
python3 tools/deck_probe.py <appid> --dry-run-request        # prints what would be asked, connects to nothing
```

`verify_profile.py` clones the copies into a temp folder, builds a fake Steam library and runs the **real Engine, the real profile and its real bundled art** over it (never the user's copies, never a Deck). It exits 0 only if every probe passes, prints one line per probe (PASS / FAIL / SKIP with the reason, plus one decisive number) and can write a JSON report. A giant archive is not copied: the folder holds the extracted regions (`<region key with / as _>.bin`) and a sparse stand-in archive is built from them, with random sentinels around every region, so a 56 GB file costs nothing.

| Probe | What passing proves |
|-------|---------------------|
| `pinned` | every copy matches the profile's pinned size and SHA-256 (the rest is skipped when it does not) |
| `cycle` | ps, ps again, original, ps, xbox, ps, original: the whole-tree hash map after each step; Original equals the start; only the profile's files change; markers/headers; backups equal the originals; no stray temp |
| `revision-upgrade` | an older revision or older art is rebuilt from the backups, equals a fresh apply, and Original is still exact |
| `running` | a running game (path, SD-card alias, `Z:\`, `AppId=<id>` only) defers with writes forbidden; `AppId=<id>0` does not |
| `steam-verify`, `new-build` | restored files are re-applied by the watcher and equal a fresh apply; a new build id gets the note; an update still downloading defers |
| `unknown-build`, `assets` | one changed byte or an unusable picture refuses the apply with nothing written and no backup folder; Original still works |
| `crash` | a power cut at write event 0, 1, middle, last-1 and last of apply and of restore, as an exception and as a hard `os._exit(9)` in a child process (torn write): every unit stays recoverable and the next sync gives the exact tree |
| `symlinks`, `ledger` | (loose files) a link, folder or 3 GB sparse file is not ours; a lost ledger or a pixel-only update is refused or left alone, never guessed |
| `timings`, `visual`, `catalog` | first/warm apply, restore, preflight and watcher tick; contact sheets (`--sheet`, needs Pillow); `build_button_catalog.py build --check` |

Which probes a kind runs is in the tool's docstring (the config-value kind has no art and no Steam-verify step; the forge kind is driven per write event, torn writes inside one entry are covered by `tests/test_entries.py`). Every probe has a mutation test in `tests/test_verify_profile.py`: when the safety property is removed from the engine, the probe must go red.

`deck_probe.py` is one file with two modes. The remote part is a stdlib-only, read-only program that the host sends on stdin of `deck.sh 'python3 -'` (so no game path is on a command line). It reports the Steam library spelling and the appmanifest, the filesystem and mount options (journaled or not), free space, owner and mode, the SHA-256 of every pinned file or region range against the table, the processes that mention the game and whether the plugin's own `steam.is_running` sees them, the installed plugin and its config (only styles and last events), the backups' size and leftover `*.button-glyphs.tmp` files. It exits 0 (no FAIL), 1 (a FAIL) or 2 (Deck unreachable).

## Triage a game before the recon

`tools/triage_game.py` is a read-only, bounded first look at an install folder. It turns the first hour of a recon into one JSON and 25 lines:

```bash
python3 tools/triage_game.py <install dir> [--json out.json] [--max-files N] [--keywords a,b] [--time-budget S] [--probe-kb KB]
python3 tools/triage_game.py --appid <id> [--json out.json]     # the Deck must be awake: .claude/scripts/deck.sh --check
```

It reports the install size and file counts, the extension histogram (top 25 by count and by bytes), engine verdicts with their evidence and a confidence (Unity, Unreal, GameMaker, MonoGame/XNA/FNA, Godot, RPG Maker, Ren'Py, Electron/NW.js, Source, id Tech, Remedy Northlight, Ubisoft Scimitar/Anvil, CRI CPK, Dimps EMB, Bethesda, Frostbite, or `unknown`), the .NET/Mono/IL2CPP runtime, containers by magic bytes (largest first), texture formats of a sample (DDS fourcc/DXGI, PNG, TGA, KTX, XNB surface format), an entropy hint for the largest archives ("likely encrypted or compressed", nothing more), the top 60 prompt-like paths (keyword score, then small pictures in UI folders; every folder keeps its best few), names inside archives that can be listed without decompressing (CPK TOC, forge name table, zip central directory, the `.xml` next to an `.rmdp`), whether Xbox/PS/Switch variant sets exist by filename, input-layer files (`xinput`, SDL, Steam Input), config files with a button/controller key, and strategy leads with "what to check next". Every conclusion is worded as a lead ("likely", "possible", "check").

Safety: it never writes, never follows a symlink (links are counted and listed), never hashes or reads a file whole. A file is opened for 64 bytes of magic; the few extras have constants in the file (512 bytes of header for a sample of textures and for the ranked candidates, 4 KB of the first bytes of the three largest containers, config files up to 256 KB, an archive index up to `--probe-kb`). The walk stops at `--max-files` entries (default 200000) and at `--time-budget` seconds (default 60) and then says `truncated`. In host mode the Deck gets the same code on stdin of `deck.sh 'python3 -'` with a JSON request that holds the appid and the limits, never a game path (exit 2 when the Deck is unreachable). `tests/test_triage_game.py` proves the bounds with spies on every write primitive and every byte read. Saves and the Proton prefix are outside the install folder and are not read.

## Releases

Releases are automatic: **every push to `main` is released**, so the release never lags behind the code. CI runs the tests, builds the zip and publishes it as `vX.Y.Z` (with a `.sha256` and generated notes). The version is decided by `scripts/ci_version.py`:

- `package.json` carries a version that has no release yet (you bumped it by hand, e.g. for a new minor): that version is released as is.
- Its release already exists at another commit: CI bumps the **patch** (0.3.1 to 0.3.2, the next free one), moves what is under `## [Unreleased]` in [CHANGELOG.md](../CHANGELOG.md) to `## [0.3.2] - date`, builds the zip with that version, commits `chore(release): v0.3.2 [skip ci]` to `main` and publishes the release at that commit.
- A re-run of the commit that was already released does nothing. A pre-release (`X.Y.Z-beta.1`) is never bumped automatically. Pull requests build and test but never release.

Things to know:
- The bot adds a commit to `main` after each release: **`git pull --rebase` before your next push**.
- If `main` moves while a release run is going, the bot's push is refused and that run fails without publishing; the run of the newer commit releases both.
- Pick the version yourself ([semantic versioning](https://semver.org)) when it is more than a patch: minor for a new game or feature, major for breaking changes. Put the line in `## [Unreleased]` of the changelog in the same pull request.
- Contributors normally **do not bump the version**. Docs-only pushes to `main` are released too.

## Conventions

- Code, identifiers, docs and UI strings are in English. A short Portuguese README exists for users; keep it in step when the English one changes.
- Module docstrings explain *why* (format facts, the failure a rule prevents), not what the next line does.
- Small, focused commits; messages in the imperative (`Add Quantum Break profile`). The pull-request template lists what reviewers check.
